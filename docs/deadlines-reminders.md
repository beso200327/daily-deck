# Completion deadlines and reminders

Estimated duration is no longer an editable or displayed field. Optional Complete by stores a local wall time independently of legacy duration data. No deadline clears time/reminder preference. Old duration values remain legacy archival metadata and are never interpreted as hours or minutes of a deadline. Additive optional fields keep both version-1 stores and old backups readable; invalid new metadata fails without resetting data.

One-time deadlines belong to their original scheduled civil date, including carryover tasks. Recurring deadlines apply to each selected weekday. New occurrences snapshot the deadline. Deadline/preference edits update only unfinished one-time occurrences or unfinished habit occurrences dated today onward, without changing deck order. Past and completed/skipped snapshots remain intact. Habit weekday/text edits retain the documented tomorrow/effective-date policy. A separate dated deadline ledger supports backfill and timezone reversal without using today's deadline on older dates. Cards, queue, habit/task management, widget preview and history show By plus the user's local time format. Overdue is a visual state, never a completion/skip/failure event. Past habit history still follows its pre-existing missed-day policy.

Local calendar construction uses the device timezone. A nonexistent DST wall time rolls forward by the gap (02:30 → 03:30 for a one-hour gap); an ambiguous fold uses its first occurrence. Reminder time is 30 elapsed minutes before the resolved deadline, including previous-day reminders for shortly-after-midnight deadlines. Already-passed reminder times are not queued; the form/details explain that no advance reminder remains. Later retains the original deadline and reminder identity.

## Native iOS implementation

The core planner produces stable entry-ID/civil-date identifiers. UNUserNotificationCenter schedules one-off local notifications with the body `30 minutes left to complete: [title]`. The user first sees a purpose explanation and explicitly chooses Continue before the app requests authorization; launch, foreground, form opening and widget actions only read settings. Denial does not block saving. iOS notification permission/settings and Focus control actual delivery.

The shared App Group journal records queued/consumed configurations. App and widget reconciliation serialize through a shared notification lock; an async queue prevents actor reentrancy from deadlocking that lock. Reconciliation reads the latest deck, removes canceled/replaced requests, and avoids requeueing a consumed deadline configuration after reload, title changes or travel. An actual deadline-time edit can replace an old delivered configuration; Later/reload/timezone changes cannot rearm the same time. Completed/skipped/deleted occurrences are excluded. Successful deck writes immediately cancel known stale requests, then reconcile. Widget actions await reconciliation; notification errors do not prevent the widget's already-persisted action from refreshing. Foreground presentation rechecks current pending state, fingerprint and timeliness.

Native status distinguishes a saved deadline/checking state, denied/failed scheduling, and OS-accepted queued identifiers. Stale async reports cannot claim a newer edit was scheduled. The queue holds at most 60 upcoming requests over a 30-day horizon, leaving capacity within iOS's 64-request limit. Reopen to extend the horizon; indefinite delivery while never reopening is not promised. Requests use resolved UTC calendar instants to disambiguate DST folds. Active/foreground, local calendar-day, timezone and significant-clock changes reconcile. While closed after a timezone/clock change, queued instants retain the last planned timezone until the app next runs; this is a native local-queue limitation. Focus, notification summaries, locked-device policy and OS scheduling may delay or suppress delivery. Closed-app delivery has not been verified here.

## Web/PWA limitation and required setup

The repository has no push subscriptions, VAPID setup, push-event handler or durable backend scheduler. Browser timers and a cached service worker cannot reliably wake a closed app at a deadline. The web checkbox saves an explicit preference only, with a visible “not scheduled” status. The reminder checkbox does not request permission, start a timer notification, upload data or claim background delivery. The separate Help & settings notification diagnostic can request permission after an explicit tap and send a real immediate system test on supported desktop browsers; this is not deadline scheduling. iPhone controls remain unavailable until Home Screen Web Push infrastructure is configured. See [exact testing steps](four-fixes.md). A denied browser permission cannot block saving. Native and web decks remain separate and do not sync.

Reliable web delivery requires an HTTPS Web Push service: explicit opt-in/purpose and supported browser/PWA installation (iOS Web Push requires a supported installed Home Screen web app), service-worker push handling, VAPID keys managed through deployment secrets, a subscription registry, a durable UTC-aware scheduling/dispatch queue, authenticated/idempotent occurrence updates and cancellation for Done/Skip/delete/deadline edits, and delivered/expired subscription handling. The scheduler must receive the minimum deadline/pending-state data; it cannot inspect closed browsers' localStorage. That would introduce backend data processing and require owner decisions on privacy, retention, security and consent. None of this infrastructure, paid services, accounts or credentials was added. Do not paste secrets into chat.

## Validation and remaining device checks

Pure web/Swift tests cover 14:00/13:30, Later stability, terminal actions, edits, history snapshots, legacy migration, selected weekdays, midnight, DST gaps/folds, travel, permission gating and consumed receipts. Browser tests cover the form, denied/unavailable permission, no prompt, no-deadline reset, persistent labels/preferences, overdue without resolution, edit without reordering, habit rollover and historical snapshots. See web VALIDATION.md for counts.

Linux Swift core tests and syntax parsing do not compile SwiftUI/UserNotifications against an Apple SDK. Before release use Xcode with the existing App Group signing setup and a real iPhone: grant/deny permission; save a 14:00 deadline before 13:30, close the app and verify exactly one 13:30 notification; repeat with Done, Later, Skip, deletion and changed deadline; create at 13:45 and verify no advance notification; check weekdays/midnight/DST/timezone, the 60-request horizon, widget cancellation, Focus/locked-device settings and app relaunch. These native API/device checks remain unverified, including extension notification-center behavior. No manual deployment was performed; pushing GitHub may trigger existing Vercel automation.
