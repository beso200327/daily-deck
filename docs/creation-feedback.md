# New-card ordering and feedback

New one-time tasks, and a new habit's occurrence scheduled for the local save date, receive an initial order strictly before today's pending cards. This happens inside the existing locked persistence transaction. Existing occurrence IDs, records, event logs and relative order do not change. Reopening retains the saved order. Editing an existing definition does not prepend it; unscheduled habits create no Today occurrence. The initial starter routine retains its familiar walking/reading/water order.

A successful creation closes the editor after persistence and opens Today with the newly created card active. A short entrance and fading lime outline provide feedback without a success toast. A polite live region announces creation, including repeated identical titles, without programmatic focus transfer. Other-day habits open Habits instead. Editing retains its prior temporary save notice.

The sidebar's own scroll port reveals the newly inserted first item; desktop page position is unchanged. After modal background-scroll restoration, mobile scrolls the new active card into view only if needed. Reduced motion disables the entrance translation and uses a brief highlight and instant reveal. The highlight timer cleans up on changes/unmount and is not persisted.

The editor's existing Saving state and synchronous guard cover image storage and the deck write. Duplicate submissions are blocked while a Web Lock waits. Photo storage failures, localStorage failures and free-plan gates retain the draft and do not show success or promote an unsaved card. Photo sources/crops remain local in IndexedDB, referenced by the saved occurrence.

Validation includes empty/existing decks, original-order preservation, Later/Undo, editing, selected/excluded weekdays, immediate shared counts/preview state, reload, no creation toast, accessible announcement, a scrolled sidebar, mobile reveal, blocked writes/retry, rapid clicks, reduced motion and photo creation/reload. Existing free-plan quota and photo-draft upgrade tests run in the complete browser regression suite. Native iOS code and storage are unchanged. Browser validation uses Chromium desktop and iPhone-sized touch emulation; actual Safari/installed PWA scrolling and VoiceOver still require device checks. No manual deployment; a normal main-branch push may trigger existing Vercel automation.
