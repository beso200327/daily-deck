# Habit deletion

The old behavior deliberately archived only the habit definition, leaving today's pending card, and placed confirmation controls at the end of the edit form. Both web and native deletion now archive the stable habit ID and record a distinct deletion for its unfinished occurrences dated today or later. This includes Later/postponed and pre-generated future occurrences. Past occurrences and completed/skipped records, even today, remain unchanged. Definition archiving releases the free habit slot and prevents generation after launch/resume/rollover. Titles are never used to match relationships.

Deleted occurrences remain inspectable as deleted records, not completion, skipping or failure. Future deletions retain their future civil date rather than appearing as extra cards in today's history. Completion percentages exclude deletions from their denominator. Undo cannot reopen a completed/skipped card after its parent habit is deleted. No photo garbage collection runs during deletion: task and historical references plus IndexedDB sources/crops remain intact.

The web editor opens a separate top-layer native HTML modal dialog with the requested title/message and destructive confirmation. Cancel/Escape returns to the unchanged draft and restores trigger focus without scrolling it. The background stays locked and inert. Both actions fit in a 320 px viewport even after scrolling the edit form. A synchronous submission guard plus shared write lock blocks duplicate actions. Failed persistence leaves the dialogs and saved data intact, displays retry guidance, and allows retry; successful persistence closes both dialogs and updates all surfaces from the shared snapshot. The native editor uses a SwiftUI alert above its form. Native core deletion is written through the shared App Group store; the existing model reloads WidgetKit timelines after successful changes. The web preview and native widget remain separate, unsynced products.

Validation covers pending, Later, completed, skipped, unscheduled, future occurrences, preserved historical snapshots/photo IDs, unrelated same-title one-time tasks, capacity release, reload/date advance, Cancel/Escape/focus, 320 px scrolled forms, storage failure/retry and deletion-neutral completion percentages. See web VALIDATION.md for final results. Swift core tests run on Linux; SwiftUI alert presentation and actual WidgetKit updates still require Xcode and an iPhone/simulator. No manual deployment; pushing may trigger existing Vercel automation.
