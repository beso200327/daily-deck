## Persistence, conflicts and offline behavior

`daily_deck_sync` serializes transactions with an account-scoped advisory lock and revision row. Ownership always comes from `auth.uid()`, never a supplied owner. The expected-user argument binds the request to its initiating account. Public RPCs validate allowed fields, relationships, pending/terminal transitions, schedule effective dates and action targets. The server creates occurrences and event sequences; ordinary writes send intents, **not replacement snapshots**. Done/Later/Skip require the exact next pending occurrence ID. Undo must target the same occurrence's last eligible action on the current local date; archival blocks resurrection. Deletes archive definitions and append deletion events only for unfinished today/future occurrences, preserving finished/past history.

Normal writes require the current account revision. Forms retain the revision they were opened against, so a foreground refresh cannot silently upgrade a stale draft. Conflicting writes reject with `40001`; the app does not merge fields or silently retry against newer data. Revisioned, confirmed responses update Today/sidebar/counts/Progress/widget preview together; old late read responses cannot roll the displayed revision backwards. Reordering keeps stable occurrence IDs and existing animations. Newly created today-selected habits/tasks enter at the top; other-day habits remain in Habits. Current free allowances (5 active habits, 10 active one-time tasks) are server-checked for new creation; import preserves existing over-limit records and does not implement paid entitlements.

An operation UUID plus its exact request is persisted **per account and request before a write**. Concurrent tabs use separate journal keys and immutable per-import backup IDs, so they cannot replace another request’s recovery data. A tab rechecks the shared durable journal before starting another mutation. The server retains a durable receipt. Reusing the UUID with a different body fails; retrying it never repeats events/imports. A lost response is resolved using `daily_deck_sync_status` before uploading again. Interrupted requests remain explicitly unresolved, not “saved.” **Retry pending save** uses the same request; do not create a replacement copy or manually delete its journal. Definite rejection clears that request but leaves the form/local deck intact. New offline edits are **not queued**. A verified active session may read its last confirmed account cache; reconnect/Retry sync before new changes. Cold offline startup cannot verify account ownership and gates cloud data behind retry/sign-in with an explicit choice to use the preserved local deck.

Refresh happens on previously opted-in login, foreground/focus/pageshow, local midnight, successful actions and manual Retry sync, with a visible-page 30-second fallback. No Realtime infrastructure is required or claimed. Device IANA timezone + the server clock determine a new action's civil date. Stored dates are not moved during travel. Unique owner/item/date constraints prevent duplication. Tomorrow-effective schedule/text edits start after the greater of today and the already-visited generation cursor; deadline changes affect unfinished today/future habit occurrences and carried one-time tasks, retaining finished/past habit snapshots. Later changes neither deadline nor completion. Pending retries retain the original local date/timezone; expired-date writes reject rather than silently becoming a new day's action. Web background reminders remain unavailable without the separately documented Push/backend implementation.

Caches, preferences, pending requests, cleanup journals and transfer backups are keyed by verified Auth user UUID. Original guest data keeps its existing localStorage key and IndexedDB database. Cloud photos use a separate per-account database. Sign-out/account switching clears in-memory account content and changes the image scope; late responses cannot populate the new account. Each cloud operation uses a data-only SDK client pinned to its verified initiating session, so switching global Auth cannot send old image data under the new account's credentials. Credentials remain in the SDK/closure memory, never deck/transfer caches or URLs. Verification waits are bounded at 20 seconds and Data/Storage fetches at 60 seconds; timeout is an unknown result requiring receipt-aware retry. An already transmitted request may finish **only in its original account**; sign-out is not a server cancellation guarantee.

Browser caches/backups are not encrypted or an account-security boundary against someone with device/devtools access. Shared-device users should sign out and manage retained browser data appropriately. Signing out deliberately does not erase the original guest deck, downloaded backups or another device's data.

## Import format and photo safety

Import is atomic for all definitions, dated snapshots, revisions and action history, and is allowed only for an empty, not-previously-imported account at the expected revision. Photo registrations/bytes are staged first; a failed/import-conflicting upload cannot partially merge a task deck. Unused private photo uploads can remain and be cleaned later. The original guest data is never deleted or overwritten, including on failed/unknown outcomes. The frozen import manifest and Blob backup are stored locally before confirmation; download a copy because browser eviction/clearing can remove them. Staging requires sufficient local storage; failure stops before upload.

Every legacy ID, including an existing UUID, is mapped deterministically to a UUIDv8 from the first 128 bits of SHA-256 of UTF-8 JSON `["daily-deck-import-v1", ownerUUID, entityType, oldID]`, with UUIDv8/variant bits set. Entity types are `item`, `occurrence`, `event`, `photo`. Relationships and Undo targets use the same map. This is a documented name-derived mapping, **not standard UUIDv5**. Different accounts get different IDs. Valid unique global event sequences are retained; missing/ambiguous sequences use a deterministic k-way merge of per-occurrence event order, next-event timestamp and original occurrence ID. Original civil dates, event instants, snapshots and crop metadata remain intact. Legacy durations remain archival values, never deadline times. Missing legacy schedule metadata starts at the saved generation cursor's next day (or creation if absent); excluded older days are not invented. Invalid/conflicting relationship data is rejected with the original backup preserved.

Photo registration is immutable and idempotent. The private bucket paths remain `ownerUUID/photoUUID/original.ext` and `ownerUUID/photoUUID/card.jpg`, with no upsert. Original source/crop metadata is retained, replacements use new IDs, and task references require **both** uploaded objects with matching size/MIME metadata. Source limit is 20 MiB, 48 megapixels; crop is an even-width 2:1 JPEG up to 1200px/1 MiB. A normalized source can exceed 20 MiB even if the selected file was smaller: choose a smaller photo; the local original is not silently discarded. Legacy photos without an edit source use their available stored image as the source; non-JPEG legacy crops are normalized for cloud storage while the original backup/source is retained. No photo library permission is requested by sync; it reads only images already stored by the app and explicitly selected new files.

Reads use authenticated SDK downloads into local Blobs. No public/signed photo URL, remote image embedding or broader CSP was added; the existing exact-project connection policy suffices. Cleanup checks **all** historical database references (including superseded same-day appearances), protects this browser's pending-upload IDs, and relies on foreign keys again inside the serialized RPC. Metadata is removed before owner-only orphan-byte deletion; interrupted file cleanup is journaled/retryable and verifies the files are gone before reporting success. Another device's in-flight upload may need a retry if cleanup wins first; it cannot silently create a dangling task/photo reference or erase referenced history. The original local image store is never a cleanup target.

The MVP reads a full account snapshot rather than adding paging/Realtime services. Import metadata is bounded to 10 MiB, 10,000 definitions and 100,000 occurrences; browser storage quota and hosted statement/request limits can reduce the practical size further; the history reconciliation ceiling is 100,000 occurrences. Existing local backup limits still apply. Larger datasets require a separate paginated/batched design; failures do not reset the original deck.

## Rollback and recovery boundaries

- To stop server cloud access, set private configuration mode to `blocked`, keep the original local deck available, and use a reviewed forward fix. Do not drop normalized records, history, receipts or the bucket; do not make photos public or restore broad client DML grants. Previous local/auth builds do not require those direct writes.
- If 003 succeeds and 004 fails, keep access blocked; do not rerun 003. Resolve the unapplied 004 error before enabling Preview. Already-applied files become immutable; subsequent fixes need a new migration.
- Unknown save/import outcome: reconnect as the **same UUID**, retry the original request, then refresh. Do not clear guest data, queues or receipts to force success. A pending import's backup stays downloadable from the initiating browser/account. If another browser populated the cloud meanwhile, the import is refused; use the preserved local deck/backup or open the existing cloud deck.
- After a partial photo cleanup, retry cleanup. Historical references remain protected. Resolve permissions/network/quota errors before claiming success; retain the original local backup. Do not manually remove referenced metadata/files.
- Database disaster recovery must restore normalized tables, head revisions, receipts, profile/configuration state and photo metadata consistently, plus corresponding private object bytes. Never restore just the revision or receipt table and resume writes. Validate in an isolated project with cloud access blocked, then reload/reverify clients. Partial restore reconciliation is an owner/operator recovery task, not an automatic client merge.

## Verification and remaining dependencies

Run `npm --prefix apps/web run build`, `npm --prefix apps/web test`, `npm --prefix apps/web run test:cloud`, `npm --prefix apps/web run test:auth`, and `python3 scripts/test-supabase-foundation.py`. The cloud browser suite runs the actual Supabase SDK with intercepted synthetic Auth/Storage HTTP and executes its transactional/Data/Storage-policy statements as authenticated roles on real disposable PostgreSQL. Storage byte responses are an in-memory fixture, and Auth JWT signatures are simulated. It is not a full hosted Supabase stack. Containers have no network/published ports, no hosted credentials, read-only SQL mounts, and are removed with their volumes.

The repository validation record distinguishes these checks from hosted tests. Real hosted JWT/PostgREST/Storage bytes and isolation, SMTP/provider configuration, live Preview response headers and real iPhone Safari/PWA behavior still need owner verification. Approved operator/privacy/terms documents, versioned acceptance, and hosted verification of account-data export/erasure remain public-release dependencies. The additive implementation and exact deployment steps for new migration 005 and the trusted Edge worker are in [ACCOUNT_DATA.md](ACCOUNT_DATA.md); do not rerun migrations 001–004. **Download pre-import backup** exports the original guest snapshot, not ongoing cloud account changes. Native authentication/sync, payments and a new launch-readiness claim are not included.

Ordinary task/habit deletion still preserves history. Explicit, recently authenticated **account erasure** is a separate trusted server operation; its scoped lifecycle job may erase owned history and receipts only through the service-only functions in migration 005. It never broadens browser DML permissions.
